# Parkdex accounts, progress backup, and interaction contract

This contract implements the approved [accounts and interactions plan](accounts-and-interactions-plan.md). This Parkdex app owns its identity and progress in its Neon database. The legacy Parkdex service supplies behavior to port, not a runtime dependency or credential migration. The user approved functional account screens using Parkdex's current styling while a later Claude design remains optional. Kip is the mascot. This document defines the shared implementation boundaries.

## Repository boundaries and ownership

| Owner | Files and responsibility |
| --- | --- |
| Auth | `database/migrations/accounts_001_init.sql`, new `worker/accounts/auth*.ts`, auth tests. |
| Native identity | Android Credential Manager and secure session bridge, Android App Links and backup exclusions, and a narrow TypeScript native identity adapter. |
| Progress backend and photos | `database/migrations/progress_001_init.sql`, new `worker/accounts/progress*.ts` and `worker/accounts/photos*.ts`, claim/photo API, private media service adapter, and backend tests. |
| Personal store and sync | `src/lib/accounts/personalStore*.ts` and `src/lib/accounts/progressSync*.ts`, legacy migration, local durability, restore, and account partition tests. |
| Interactions | `database/migrations/interactions_001_init.sql`, new `worker/interactions*.ts`, `src/lib/interactions/**`, event tests and retention endpoint. |
| Integration and delivery | Shared `worker/index.ts`, `api/feedback-api.ts`, `vercel.json`, `package.json`, runtime variables, delivery scripts and migration inventory, provider resources, account UI wiring, preview and staging lifecycle. One owner should integrate changes to these shared files. |

The delivery harness must first support both new additive migrations and all required runtime values. That tooling bootstrap goes to staging before the feature. Keep `kip_feedback`, `kip_account`, and `kip_analytics` separate. Existing feedback operator credentials and cookies cannot authenticate consumer accounts.

Server modules export `handleAuthRequest(request, env): Promise<Response | null>`, `handleProgressRequest(request, env, auth): Promise<Response | null>`, and `handleInteractionRequest(request, env): Promise<Response | null>` for their owned routes. `null` means the route is not owned. Auth exports canonical `authenticateAccount(request, env): Promise<AuthContext | null>` with `AuthContext = { accountId: string; sessionId: string; transport: 'cookie' | 'bearer' }`; a `requireAccount` wrapper may throw or return a `401` for protected routes. Auth also exports a trusted Origin and CSRF guard for cookie writes. The integration owner routes requests and supplies context to progress handlers. A missing context on a progress route returns `401`. The retention handler is separate and protected by `KIP_RETENTION_SECRET`.

## Identity and sessions

`kip_account.accounts` has an immutable UUID primary key, normalized unique email, nullable Argon2id password hash, optional display name, email verification time, creation time, and a deletion state. Use Argon2id with at least the legacy parameters of 19 MiB, two passes, and one lane. `kip_account.google_identities` has a unique `(provider, subject)` and an account foreign key. Once linked, Google's `sub` identifies the account even if Google's email changes. A matching email alone never links, merges, or transfers accounts. A collision returns a safe conflict and offers a signed-in, recently reauthenticated linking flow. New Google identities without a collision create a new Parkdex account. Do not copy old Parkdex credentials or accept old service sessions.

Store only SHA-256 hashes of 256-bit random session tokens in `kip_account.sessions`. Each request looks up the active, unexpired token and derives the account ID from that row. A client-supplied account ID is never an authorization source. Logout revokes the current token, password reset and deletion revoke all tokens, and session renewal rotates the token atomically. Use a documented 30-day sliding expiry and a 90-day absolute reauthentication limit, renewing only when less than seven days remain. Bind each token to one device/session row and test concurrent renewal so the previous token cannot remain valid. Hash single-use, one-hour verification and reset tokens. Keep the legacy generic password-reset response, login and registration rate limits, verification flow, and security events with hashed scopes rather than raw email or tokens. Email delivery uses the existing configured Resend sender with separate auth templates and exact staging or production link hosts.

Web sessions use a `Secure`, `HttpOnly`, `SameSite=Lax` cookie with an explicit path and no persistent bearer token in localStorage, IndexedDB, or JavaScript-readable cookies. Protect state-changing cookie requests with strict trusted-origin checks and a CSRF token. The CSRF token is scoped to the session, supplied in a header, and checked server-side. Native Android uses an `Authorization: Bearer` token held only in Android Keystore-backed secure storage through a Capacitor bridge; it does not use the web cookie. Exclude encrypted credential material from Android Auto Backup and device transfer. Do not put either form of token in URLs, telemetry, crash logs, or photo keys.

Every `/api/claims` request and account-scoped authenticated mutation includes `X-Kip-Account-ID` with the immutable account ID captured by the calling UI session. The server requires it to match the account derived from the cookie or bearer token before reading progress or mutating account state. It is a mismatch guard, never an authorization source. This prevents a stale browser tab for account A from uploading its local partition or deleting/reauthenticating account B after another tab replaces the shared cookie. Account-scoped mutations include session renewal, logout when a session exists, verification request, Google reauthentication/link challenge and completion, password reauthentication, and deletion. Sign-in, registration, password-reset and verification token confirmation, Google sign-in, and `/api/auth/me` do not require the expected-account header. Client requests and delayed responses remain bound to the captured account ID and session generation; a later account switch cannot commit an older response to the new account's UI or local partition.

Android Google sign-in uses Credential Manager in a Capacitor bridge, with a server-issued, single-use, short-lived nonce. The server verifies Google's ID-token signature, issuer, configured web-client audience, expiry, verified email, nonce, and stable `sub`. It consumes the nonce once and rejects replay. Configure OAuth for each Android package/signing identity, including debug, field, and Play app signing certificates. Google allows each package and signing fingerprint pair in only one Cloud project, and `app.parkdex`'s Play signing fingerprints belong to the staging project. So an environment whose web client lives in another project sets the optional `GOOGLE_NATIVE_CLIENT_ID` to a web client from the project that owns the Android registrations. `GET /api/auth/config` returns it as `googleWebClientId` to native app requests (origin `https://localhost` or `capacitor://localhost` together with `X-Kip-Auth-Transport: native`), because installed builds pass that field to Credential Manager as `serverClientId`. Web requests keep `GOOGLE_WEB_CLIENT_ID`. Both Google token endpoints accept an ID token whose `aud` is either configured client. Identities stay keyed by Google's `sub`, which is the same for one Google account across Cloud projects, so existing links keep matching. Never run Google's OAuth page in the WebView. The iOS app signs in to Google with an iOS-type OAuth client (bundle ID `app.parkdex`) through `ASWebAuthenticationSession` with PKCE, the system browser sheet Google allows. `GOOGLE_IOS_CLIENT_ID` names it: `GET /api/auth/config` returns it as `googleWebClientId` to iOS requests (origin `capacitor://localhost` with the native transport header), and the Google endpoints accept it as an audience. Without it iOS builds show no Google button. Verification and reset emails return through verified Android App Links and the Capacitor App listener on the matching environment host. Web links must work as well. The client consumes and clears link tokens immediately.

### Sign in with Apple (iOS)

App Store guideline 4.8 requires Sign in with Apple wherever the iOS app offers Google. It exists only in the iOS app (`AuthenticationServices`, `NativeIdentity.getAppleCredential`); Android and the web are unchanged.

- **Verification.** `worker/accounts/apple.ts` checks the identity token's RS256 signature against Apple's published keys (`https://appleid.apple.com/auth/keys`, cached for an hour and refreshed once for an unknown key ID), issuer `https://appleid.apple.com`, audience `app.parkdex`, expiry and the server nonce. The app passes the server nonce to Apple unchanged, so the token's `nonce` claim must equal it. Nonces come from `POST /api/auth/apple/challenge` and are stored in `kip_account.google_challenges` with `provider = 'apple'`; a Google nonce never completes an Apple sign-in, or the reverse.
- **Identities.** `kip_account.apple_identities` mirrors `google_identities`, keyed by Apple's `sub`. Apple shares the name only on the first sign-in on a device and may send no email later, so the subject alone finds an existing account. A new account needs an email, which Apple always provides when the person shares it or uses Hide My Email (a `privaterelay.appleid.com` address). Without one the route answers `apple_email_required`, because an account without an email would look like a guest.
- **Linking.** Apple works exactly like Google: `sign_in`, `reauth` and `link` purposes, no auto-linking by email (a matching email answers `account_conflict` and asks the person to sign in the other way and link Apple), a five-minute reauthentication before linking, and guests upgrade in place with the Apple email. So a person can hold Google, Apple and a password on one account, and an Apple ID or Google account can belong to only one Parkdex account. This reuses the Google code path instead of keeping the providers apart, which would need its own rules for email collisions.
- **Revocation (guideline 5.1.1(v)).** With `APPLE_TEAM_ID`, `APPLE_SIGN_IN_KEY_ID` and `APPLE_SIGN_IN_PRIVATE_KEY` (the Sign in with Apple `.p8`), every Apple sign-in, reauthentication and link trades the one-time `authorizationCode` for a refresh token at `https://appleid.apple.com/auth/token` and keeps it AES-256-GCM encrypted (key derived from `AUTH_SESSION_SECRET`) in `apple_identities.refresh_token_ciphertext`. Account deletion revokes each kept token at `https://appleid.apple.com/auth/revoke` after private data is gone and before the account rows are deleted. Revocation is best effort and never blocks deletion; each outcome is a `apple_revoke` security event (`revoked`, `failed`, `unreadable`, `not_configured`). Without the key, sign-in works and nothing is sent to Apple. An Apple-only account must reauthenticate with Apple before deletion, which hands the server a fresh code, so turning the key on later still revokes accounts deleted after that.

### Auth HTTP surface

| Endpoint | Request | Result |
| --- | --- | --- |
| `GET /api/auth/config` | None | Email, email delivery, web Google, native Google capabilities and the configured public Google client ID; `appleEnabled` for iOS requests. |
| `POST /api/auth/register`, `/api/auth/login` | Normalized email and password, registration may include display name | Account and session. Native response contains bearer token; web sets the session cookie and returns no bearer. |
| `POST /api/auth/google/challenge`, `/api/auth/google/native` | Challenge request, then ID token and nonce | One-time challenge, then account and native session. |
| `POST /api/auth/apple/challenge`, `/api/auth/apple/native` | Native only. Challenge request, then `{identityToken, nonce, authorizationCode?, givenName?, familyName?}` | One-time Apple challenge, then account and native session (or reauthentication or link, by purpose). |
| `POST /api/auth/reauth/password` | Current session plus password | Mark the session recently reauthenticated for five minutes. Google uses a `reauth` challenge followed by the normal web or native Google token endpoint. |
| `GET /api/auth/me` | Authenticated | Account ID, email, verification state, display name, and linked providers. |
| `POST /api/auth/sessions/renew`, `/api/auth/logout` | Authenticated | Rotated session or revocation. |
| `POST /api/auth/verification/request`, `/api/auth/verification/confirm` | Authenticated request, then one-use link token | Generic request result and confirmation. |
| `POST /api/auth/password-reset/request`, `/api/auth/password-reset/confirm` | Email, then one-use token and new password | Generic `202`, then confirmation and all-session revocation. See Account recovery below. |
| `DELETE /api/account` | Freshly reauthenticated session and CSRF on web | Starts deletion, revokes sessions, removes personal rows and private objects, and returns a durable deletion receipt/status. |

All auth responses are `Cache-Control: no-store`. JSON input has explicit size limits. Reject malformed or extra security-sensitive fields. Authentication and account deletion need per-action rate limits. Password reset never reveals whether an email exists. Deletion is idempotent: persist a deletion receipt and object inventory so a partial R2 failure can be completed by an explicit operator recovery command without a scheduled retry service. Mark an account as deleting before revocation and reject new writes. The UI cannot report deletion complete until personal Neon rows and private objects are removed. The operator receipt may retain opaque object keys only until cleanup is confirmed and must not retain email, photos, or credentials.

Google challenge requests are `{purpose: 'sign_in' | 'reauth' | 'link'}` and return `{nonce, expiresAt}`. Token requests are `{idToken, nonce}` at `/api/auth/google` for web cookies or `/api/auth/google/native` for native bearer sessions. Store only a hash of the nonce, bind reauthentication and linking challenges to the current account/session and transport, expire them quickly, and consume once in a transaction. A link requires a current account and five-minute reauthentication. Auth's account deletion service invokes a progress/photo cleanup callback supplied by integration; partial cleanup leaves a durable pending receipt. An authenticated operator can explicitly resume it with a same-origin `POST /api/operator/account-deletions/:receiptId/resume`; pending work never creates a retry service.

### Account recovery

`POST /api/auth/password-reset/request` always answers `202 {"accepted":true}` with the same headers, and reserves the same email and IP rate limits, whatever the email belongs to. What it sends depends on the account:

| Account | Email | Security event on delivery failure |
| --- | --- | --- |
| Active, has a password | "Reset your Parkdex password" with a one-use, one-hour reset link. | `password_reset_email` |
| Active, Google sign-in only | "How to sign in to Parkdex": the account uses Google, so tap "Continue with Google" with this address; no password is needed. It links to the account page and issues no token. | `password_reset_google_email` |
| Unknown or being deleted | Nothing. | none |

The Google directions go only to the account's own inbox, so they reveal nothing to the requester. A Google-only account never receives a reset token and cannot gain a password through reset. Email goes out through `waitUntil`, so the response never waits on the provider. When email delivery is not configured (`emailDeliveryEnabled` is false in `/api/auth/config`), the route answers `503` and the app hides "Forgot password?".

## Guest accounts

A player who picks a @handle at onboarding plays without signing in, as a guest account (`POST /api/auth/guest`, migration `accounts_002_guests.sql`).

- **What a guest is:** an account with no email and no password (`normalized_email IS NULL`). `/api/auth/me` and session responses carry `guest: true`. The app opens one when a handle is waiting on the device and nobody is signed in (`src/lib/accounts/guestStart.ts`), once per launch and once right after onboarding, then claims the handle and its flag for it. Signing out clears the waiting handle, so leaving an account never opens a new guest.
- **Limits:** 20 guest accounts per address an hour, and 300 everywhere per 15 minutes.
- **Sessions:** the session on the phone is the guest's only credential. It slides for 365 days, renews once it is 30 days old, and is capped at 10 years. The phone asks to renew on that schedule (`nativeSessionNeedsRenewal`), and after an upgrade it takes the server's shorter expiry.
- **Upgrade:** Google upgrades a guest in place through the `link` purpose. It needs no reauthentication, and the account keeps its ID, handle, flag, points and backups. The account takes the verified Google email, and its sessions shorten to an ordinary account's limits (30 days sliding, 90 days total).
- **Conflicts:** a Google subject or email that already belongs to another account is refused with `account_conflict`, and the guest is left unchanged.
- **Deletion:** a guest deletes its account without reauthenticating. Leaving a guest account (sign-out) loses it for good, and the Account screen says so.
- **Abandoned guests:** a guest nobody can open any more is deleted 30 days later. That covers a guest that left, was uninstalled, or went a year without opening Parkdex.
  - **Rule:** no live session, and nothing about the account happened in the last 30 days (its creation, or a session's revocation or expiry).
  - **How:** the daily retention run (`purgeAbandonedGuests`) uses the ordinary deletion path, resuming up to 10 stuck deletions and starting up to 10 new ones within 20 seconds. A failure there never fails the rest of the retention run. Private photos go first, then the account, and its @handle, flags and points cascade with it. A deletion left pending is resumed on the next run.
  - **Why 30 days:** a guest's session is its only credential, so nobody can reopen the account once it has none. The grace period only covers clock skew and in-flight requests, and keeps the handle reserved for a month in case the player comes back to look for it.

## Durable local claims and account boundaries

The existing tester data is `localStorage['parkdex-mockup-v1'].claims[parkId] = {at, photo: ''}` plus IndexedDB `parkdex/photos[parkId]`. Migrate this in place once into a new transactional local claim/photo store. Each existing claim receives a random UUID exactly once, persisted with its original park ID, original claim time, and the corresponding photo before any network request. Retain the old storage until the new transaction commits; repeat migration safely after a crash. Do not use a new Android package or signing identity. New claims also receive a UUID and commit claim metadata and the local photo durably before the UI announces success or emits `park_claimed`. If the local write fails, preserve the capture and show a retryable error. Claims and photos remain separate from downloadable content storage and survive a content release or retired park.

Legacy metadata has no park snapshot. Its local migrated record may temporarily hold `parkSnapshot: null`. Resolve the snapshot from the active or retained content catalogue, persist it locally, and only then upload the full immutable claim. Never fabricate a park display record or drop a claim because its details are temporarily unavailable. Show backup pending and retain the local record for explicit recovery if no content copy can be found. New claims always capture the complete `Park` snapshot at local commit.

For an earned park retired before restore on another device, use the claim's immutable `contentReleaseId` and frozen `parkSnapshot.scene` to recover its original public scene art. Historical content releases remain available at the approved CDN. Validate the archived manifest's exact release ID, strict schema, approved file paths, and content-addressed inventory digest before selecting the scene file. Verify the art bytes against that manifest's size and SHA-256, then retain a local public-art descriptor and bytes keyed by release ID and scene so accounts with different claim vintages cannot overwrite one another's art. Display the frozen park snapshot and its matching archived art even when the current catalogue no longer contains the park. This requires no additional claim or server schema field. On offline restore, keep the original claim and show art as pending until the verified archived asset can be downloaded; do not substitute unrelated current-release art as the original.

Partition local data by `guest` or immutable Parkdex account ID. On the first verified sign-in, atomically reserve each unassigned claim for that account and copy its immutable metadata and exact photo bytes into that account's partition. Hide reserved guest rows immediately. Keep their recovery copies until the server acknowledges each claim and its supported photo, then remove those guest rows and reservations individually. An unsupported photo needs a matching durable local account copy before removing its guest source. Preserve a unique account owner inferred from older copied claims and fail closed on conflicting owners. A second account cannot acquire already reserved claims, even before Wi-Fi becomes available.

Signing in to a different account never uploads or displays the previous account's cached claims/photos. Logout revokes the session online and hides or clears that account's local cache and token; it does not move its collection into the guest partition. If offline, do not pretend server revocation succeeded. Account deletion clears the account's local personal cache, its reserved guest recovery copies, and token after the server durably accepts deletion intent, atomically marks the account deleting, revokes its sessions, and returns a receipt. A pending receipt means private cleanup still needs explicit recovery; it does not make the account usable again. Network errors or 5xx responses without a receipt leave the local copy untouched. Unassigned progress remains separate. A restored account's claims are unioned by claim UUID; multiple historical claims for one park produce one earned badge while preserving the individual immutable records.

Claim and photo requests run while the app is foregrounded. Android requires confirmed Wi-Fi, binds requests to that network, and cancels on loss. The web app backs up on any online connection, including browsers that do not expose a physical connection type, and cancels when offline. Connectivity, foreground and new-claim events initiate coalesced sync without polling. Auth requests can use any connection. Public map and content download policies remain separate. Persist the last successful outgoing backup timestamp per account only after outbound claims and photos are acknowledged with no pending or conflicting upload. A failed, offline or restore-only pass cannot advance it. Account UI shows this compact timestamp and pending state without a separate backup card, attachment flow or manual button.

`kip_account.claims` has `(account_id, claim_id)` uniqueness, exact stable `park_id`, original `claimed_at`, bounded frozen park display/art snapshot, and server creation time. Never reference a live catalogue row with cascading deletion. The server accepts immutable claim uploads: the same account, claim ID, and canonical payload is an idempotent success; the same ID with changed fields is `409`. Distinct claim IDs for the same park remain historical records. Upload, list, and restore use authenticated, cursor-paginated endpoints. An acknowledged local sync cursor advances only after server persistence is confirmed. Network failures cannot remove local claims. A claim is never reconstructed from an interaction event.

The `PUT /api/claims/:claimId` JSON body is `{parkId, claimedAt, parkSnapshot, contentReleaseId}`. `claimId` is a UUID path parameter. `parkSnapshot` is a bounded copy of the public `Park` shape in `src/lib/parks.ts`, including the park centroid but no visitor location. It is validated and frozen at claim time. `contentReleaseId` is a string or `null`. The list response is `{claims: ClaimBackup[], nextCursor: string | null}`, where each `ClaimBackup` has `claimId`, `parkId`, `claimedAt`, `parkSnapshot`, `contentReleaseId`, and `photo: {status: 'missing' | 'pending' | 'ready', sha256?, sizeBytes?, contentType?}`. The opaque cursor is account-bound and uses a bigint change revision. Claims are ordered by revision, so a claim may appear again after its photo changes from missing to pending or ready; clients upsert by claim UUID. Pages contain at most 50 records. Every nonempty page returns a cursor for its final record, including a short final page. An empty terminal page returns `nextCursor: null`; clients preserve their previous cursor anchor. Clients persist received pages locally before advancing their restore cursor.

The separate per-account `last-complete-sync` marker supports the visible **Last synced** timestamp. It advances after a complete claim pull and photo reconciliation with saved claims, no issues, and no pending work, including a restore-only or unchanged pass. The captured session, foreground state, and platform connection policy must still be valid at commit. Keep the older outgoing-backup marker separate and retain its **Last backed up** label until a complete sync is recorded.

Local and server claim validators accept the catalogue's five categories: national, provincial, regional, municipal, and community. Unknown categories remain invalid.

A photo taken in the app (#173) is stored as its upright original, re-encoded as JPEG without metadata at most 2,048 px on the long edge and 2.5 MiB, with the player's crop beside it in the local photo row: `crop: {x, y, width, height}`, normalised 0–1 to the original's width and height, 3:4 in pixels (`src/lib/photoCrop.ts`). A missing or null crop means the largest centred 3:4 fit. Re-cropping changes only `crop` (`setPersonalPhotoCrop`); the photo bytes, digest, backup state and upload rules never change with it. My Dex (#174) makes every photo its own claim, so a park can have several. Each photo's display choices sit beside the crop in the same local row: `coverAt`, when the player made it the park's cover (the latest choice per park wins, otherwise the newest photo is the cover), and `removed`, which hides it from My Dex while the photo, its claim and its backup stay. A change bumps `displayVersion`; backup records the version it sent in `displaySyncedVersion`, so a change made while a backup is in flight stays pending.

These display choices are backed up beside the immutable claim, never in it (`database/migrations/game_005_dex.sql`, table `kip_account.claim_display`, one row per claim, removed with the claim). Each sync, after claims and photos, uploads pending choices for acknowledged claims and then restores the account's choices onto photos saved on the device, skipping any photo whose own choices are still pending. They are optional: a failed or unsupported request leaves them pending for the next pass and never marks claim or photo backup as failed, and the photo size and no-overwrite rules are unchanged. Deleting a backed-up photo is a follow-up.

Recover legacy demo SVG photos only when their bytes exactly match the app-generated scene for the claim's frozen park snapshot. A bounded raster conversion may also recover oversized JPEG, PNG, or WebP photos. Persist the resulting JPEG as a separate upload rendition; preserve the original blob, hash, owner, claim UUID, and frozen claim metadata. Reuse the saved rendition on retry and compare its hash with remote photo metadata. Unsupported or conflicting images stay local with an honest error, and server photo format, size, and overwrite restrictions remain unchanged.

### Progress and photo HTTP surface

| Endpoint | Behavior |
| --- | --- |
| `PUT /api/claims/:claimId` | Upload one immutable claim; `201` new, `200` identical retry, `409` changed payload. |
| `GET /api/claims?cursor=...` | Authenticated, account-bound revision pages including retired park snapshots and photo state. Pages contain up to 50 claims, and photo-state changes reissue the affected claim at a later revision. |
| `PUT /api/claims/:claimId/photo` | Authenticated byte proxy upload for that account's claim. JPEG, PNG, or WebP only, maximum 2.5 MiB, validated MIME and magic bytes, server-computed SHA-256. Same digest is idempotent; a different digest cannot silently overwrite a backed-up photo. |
| `GET /api/claims/:claimId/photo` | Authenticated private byte download, scoped to the owner. Never use the public content CDN. |
| `PUT /api/claims/:claimId/display` | A photo's display choices, written whole: exactly `{crop, coverAt, removed}`, where `crop` is `{x, y, width, height}` inside 0–1 or null and `coverAt` is an instant or null. Last write wins. `404` when the claim is not this account's. |
| `GET /api/claims/display` | Every display row of the account (up to 5,000): `{displays: [{claimId, crop, coverAt, removed, updatedAt}]}`. |

Use a separate private R2 bucket for personal photos behind a Cloudflare private media Worker. The Vercel account API proxies authenticated photo requests to that Worker with `KIP_PHOTO_SERVICE_URL` and `KIP_PHOTO_SERVICE_TOKEN`; no R2 API credentials go to Vercel. The Vercel adapter enforces a request cap below its platform body limit, including headers and multipart overhead; prefer raw image bytes to avoid base64 expansion. The server generates object keys from account and claim UUIDs, never trusts client object keys, and checks ownership before both upload and read. The private Worker accepts only service-authenticated requests and has no public object route. Photo backup is independent of claim metadata: a claim can be backed up while its photo is pending, with clear user-visible status. Verify hash and size on restore before replacing the local copy. The current demo camera can produce SVG; rasterize it locally for a supported image format or mark its photo unsupported, never upload SVG to this endpoint. A failed photo upload cannot roll back a successfully saved claim.

The shared client HTTP helper is `fetchAuthenticated(input: RequestInfo | URL, init?: RequestInit): Promise<Response>`. Native reads the Keystore token at request time and adds `Authorization: Bearer`. Web uses same-origin credentials and adds the CSRF header on state changes; it never exposes the session token. Sync supplies the captured account ID in `X-Kip-Account-ID` on every claim/photo request and aborts if its session generation changes. The helper must not accept an account ID to select authorization.

## Three interaction events

`POST /api/interactions` accepts a bounded batch of exact-schema events. The only types are `park_viewed` when a park detail is opened through `MapScreen.select`, `directions_opened` when one of the explicit external Maps links is requested, and `park_claimed` after a local claim transaction commits. A React render, retry, or collection badge view does not create another `park_viewed`. Direct event calls belong at those actions, not in a global click handler. Navigation and claim completion never wait for event delivery.

Each event has random UUID `eventId`, install UUID, session UUID, client occurrence time, event schema version, app version/build, content release ID, environment, and stable park ID. The server adds receipt time. `park_viewed` has a bounded `entryPoint` enum such as map, nearby, or collection. `directions_opened` has bounded provider, travel mode, and entry point enums; it records a request to open directions, not arrival. `park_claimed` has claim UUID and first-claim/repeat status. Event IDs are persisted in a local outbox and reused on retry; a conflict on the same event ID with different payload is rejected. Never include account ID, email, name, exact or coarse coordinates, IP address, photo, token, URL query, referrer, or free text in stored interaction rows or API logs. No logging opt-out is part of this product behavior. Keep claim sync and interaction delivery independent.

`kip_analytics.events` uses `event_id UUID PRIMARY KEY`, constrained type and context columns, random install/session UUIDs, park ID, client and server timestamps, schema/build/release/environment, and a payload hash for idempotency checks. It has no account foreign key. Validate exact keys and enum values at the API boundary. Reject oversized batches and timestamps implausibly far in the future or older than the retention window. The API must not persist request headers. A daily bounded retention job deletes raw rows older than 90 days and reports remaining expired rows for operator recovery. This scheduled job exists solely to satisfy the 90-day retention requirement; it is not a polling or retry worker. An authenticated manual purge command handles a missed run. Keep the retention route protected by its own secret and never expose the secret to the app.

## Runtime and verification

Recommended runtime names are `DATABASE_URL`, `AUTH_SESSION_SECRET`, `AUTH_EMAIL_FROM`, `RESEND_API_KEY`, `GOOGLE_WEB_CLIENT_ID`, optional `GOOGLE_NATIVE_CLIENT_ID`, optional `GOOGLE_IOS_CLIENT_ID`, optional `APPLE_TEAM_ID` (also serves `apple-app-site-association`) with `APPLE_SIGN_IN_KEY_ID` and `APPLE_SIGN_IN_PRIVATE_KEY`, `KIP_PHOTO_SERVICE_URL`, `KIP_PHOTO_SERVICE_TOKEN`, `KIP_RETENTION_SECRET`, and exact environment-specific `PUBLIC_APP_URL`/`ALLOWED_ORIGINS`. The Cloudflare Worker owns the R2 binding and its own service token configuration. Consumer `AUTH_SESSION_SECRET` is distinct from the feedback operator's `SESSION_SECRET`. Reuse existing names where the delivery harness already owns the same value. Keep all secrets server-side. The auth feature must report unavailable when required credentials are absent. The local stack (`docs/local-stack.md`) disables outbound email while still exercising email/password, claim sync, account deletion, and interactions with seeded test accounts. OAuth client IDs, Android package identities, and signing certificate fingerprints are provider configuration outside the auth database.
