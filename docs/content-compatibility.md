# Content compatibility with installed apps

Testers and players keep older app builds for weeks. Each build saves content on the device and keeps reading the content API after newer builds ship. These rules keep every supported build working.

## The rule for the content API: add, never break

Within `parkdex.content-sync/v1`, a server change may only:

- add a new park, boundary, drive row, badge or map release;
- change the value of an existing field to another valid value.

It must not rename, remove, or retype a field, or change what a field means. A breaking change needs a new schema version served alongside v1, or a `minimumReaderVersion` bump on the content channel so older builds keep their saved content and show the update prompt.

**Builds installed before 2026-10-01 are strict.** They reject any field, enum value (category, biome, shape, rarity), change entity or asset kind they do not know. Until those builds are retired, the server must not send any of these to them. New fields and values need to wait, or be served only to clients that ask for a newer reader.

## Catalogues larger than one response

The API and every installed build reject a content response over 4 MiB. Parks that would push the snapshot past that get a reader floor (`public.content_park_reader_floor`): readers below the floor never receive them in `snapshot` or `changes`, and a batch with only such parks reaches them as an unchanged hub list. Reader 3 builds load the whole catalogue from an immutable CDN release instead. See `docs/content-catalogue.md`.

## What builds from 2026-10-01 do

- They ignore fields added after they shipped.
- An unknown category, biome, shape or rarity shows as `community`, `forest`, `circle` or `common`.
- They skip change entities, operations and asset kinds they do not know.
- One unreadable park is left out with its boundary, drive row and badge art; the rest of the catalogue still loads. If the sync fails anyway, the app keeps showing its last good content.

## When the app starts reading a new field

1. Have the server send the field (see the strict-builds note above).
2. Make the reader treat the field as optional, with a sensible default when it is missing.
3. Bump `CONTENT_READER_VERSION` in `src/lib/content/contracts.ts`. When someone upgrades, the app keeps showing its saved content while it fetches one full snapshot, so the new field gets filled in.

## Changing on-device tables

Native SQLite table changes go in `LOCAL_MIGRATIONS` in `src/lib/content/store.native.ts`. Append a step; never edit or reorder one that has shipped. The app applies each step once, in order, and records the version in `content_local_schema`.

## The contract test

`src/lib/content/compat/contract.test.ts` runs in `npm test`. It checks that both the current reader and a frozen copy of the strict reader (`src/lib/content/compat/reader-v1.ts`) can read:

- saved real responses from the staging API (`src/lib/content/compat/fixtures/`);
- the snapshot and a change batch of every entity kind, generated by the current server code in `worker/content_sync.ts`.

If a server change would break installed builds, this test fails before merge. Refresh the saved responses with:

```bash
node scripts/capture-content-contract-fixtures.mjs https://staging.web.parkdex.app
```

When no supported build still uses a frozen reader, delete its file and its entry in `READERS`.
